# Day80：事务基础

## ACID

- 原子性（Atomicity）：同一个事务中的多个写操作不可拆分，要么全部提交，要么全部回滚。例如“扣库存、保存订单、保存订单项”中任意一步失败时，前面已经执行的写操作也不能保留。
- 一致性（Consistency）：事务开始前和结束后，数据都必须满足数据库约束与业务规则。例如订单的总金额应正确、订单项必须关联存在的订单、库存不能小于 0。事务本身不能自动创造业务规则，代码和 SQL 仍要把规则写正确。
- 隔离性（Isolation）：并发事务之间不应随意看到彼此未提交的中间状态。隔离级别决定并发读取和写入的可见范围，但默认隔离通常仍不足以阻止“先查库存、再扣库存”的超卖问题。
- 持久性（Durability）：事务提交成功后，数据应保存到数据库，即使应用进程或服务器随后异常退出，重启后已提交的数据仍应存在。

## @Transactional 的作用

- 它把哪些数据库操作包在同一个事务中？
  - 数据库的读和写包在同一个事务中
- 方法正常结束时会发生什么？
  - Spring 会提交事务，事务中的数据库写入一起生效。
- 方法抛出运行时异常时会发生什么？
  - Spring 默认回滚事务，事务中已经执行的数据库写入会被撤销。

## 当前库存代码的边界

- 为什么加了 @Transactional 仍不能完全防止超卖？
  - 事务保证多个操作可以一起提交或回滚，但两个并发请求仍可能都在扣减前读到相同库存。它不能代替原子的库存条件判断。
